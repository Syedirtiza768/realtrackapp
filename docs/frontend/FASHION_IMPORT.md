# Fashion bulk import

The shared catalog import accepts the full Artistic Server Fashion workbook through the existing Fashion import permission and maps it into reviewable `fashion` catalog drafts. The importer reads the `Item Specifics` field, source measurements, category, image URLs, source channel/account/marketplace values, price currency, and source item ID. Common specifics become curated Fashion attributes; remaining specifics are stored as paired editable `customAspectNames` / `customAspectValues` values and appear under **Additional item specifics** in the Fashion editor.

The import preserves the source measurements as editable notes and keeps the source JSON for audit. Because this export does not declare a measurement unit, the importer does not assume cm or inches; the editor requires an explicit unit confirmation before the row can publish and before a structured chart is filled. Confirmed units are included with the measurement notes in generated listing text. Source status and marketplace IDs are provenance only and do not make the imported row an existing eBay listing.

Fashion rows from this export are drafts and enter the existing authenticity review flow. The source channel status `failed`, zero quantity, and source item ID do not auto-publish or mark the listing as live. Operators edit category, condition, price/stock, descriptions, specifics, photos, and marketplace policies in the Fashion workspace before reviewing and publishing.

Each source photo is fetched with a 25 MB limit, converted/oriented to WebP, and stored under a deterministic key in the application's configured S3 bucket. Catalog image URLs and the import listing preview are updated to those WebP objects. Conversion is bounded to four concurrent images; retries reuse successfully mirrored objects. A row with any failed image copy remains editable, records expected/stored/failed counts, and is blocked from publishing until the same catalogue is re-imported successfully. If `CATALOG_MIRROR_IMAGES=false`, the import report warns that mirroring was skipped; enable mirroring before re-importing. This gate applies only to the identified source-export format; other vertical imports retain their existing image path.

The import reuses `catalog_products.vertical_attributes` JSONB and adds no SQL migration. Duplicate SKUs inside the workbook follow the standard import duplicate handling. Source analysis of `catalogue-export-2026-10-20 (1).xlsx`: 13,209 product rows, 13,205 distinct SKUs, four repeated-SKU rows, and 104,187 image URL entries. The source-specific column mapper keeps `Category Id` and `Category` separate and reads the actual `Site Id`, `Marketplace`, `Currency`, and `Images` headers. The shorter workbook with the same date omits the item specifics and image data and is not the source for this workflow. These are workbook counts, not a claim that the import has run in production.

Verification on the current `main` base: frontend and backend production builds pass, and 33 focused import/Fashion regression tests pass. No production import or deployment is implied.
